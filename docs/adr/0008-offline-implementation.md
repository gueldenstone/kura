# 0008. How offline works

- Status: Accepted
- Date: 2026-10-31

## Context
ADR 0003 decided on an installable PWA with a separate lightweight offline view. This records how it is built.

## Decision
- **Saved copy.** `Kura.Offline.snapshot/1` describes the inventory and the shopping list as plain data. `KuraWeb.LiveKitchenSync` (an `on_mount` hook on every signed-in LiveView) pushes it to the browser as a `"kura:snapshot"` event when the page opens and after every change on `kitchen:changed`; `assets/js/offline` stores it in `localStorage`. No extra request is needed to keep it fresh.
- **Offline screens.** `GET /offline` is a static shell (`#offline-root`, no data) that the service worker caches. `assets/js/offline` draws the shopping list and the inventory (read-only, with search) from the saved copy. Which tab opens is decided by the URL the phone asked for, so `/inventory` offline shows the inventory.
- **Service worker.** `/sw.js` is generated by `KuraWeb.PwaController` so it can list the current (digested) asset URLs, and its cache name changes with that list. Scope is `/`. It only acts when the network fails: navigations that time out (3.5 s), fail, or get a 502-504 from a proxy in front of a stopped app are answered with the cached `/offline` shell; assets come from the network first and from the cache otherwise (digested files cache-first). It never touches non-GET requests, the LiveView socket or `/offline/*` API calls.
- **Losing the connection while the app is open.** When the LiveView socket stays closed for 4 s and the server cannot be reached, the page reloads, and the service worker answers with the offline shell.
- **Check-offs.** Offline check-offs and un-checks go into a queue in `localStorage` (the net change since the saved copy: flipping a queued change cancels it) and are shown on top of the saved copy, including an optimistic restock. Phones send only intents (`check`/`uncheck` plus an entry id), never stock values.
- **Sync.** `POST /offline/sync` applies the queue in order through the normal `check_off`/`uncheck` actions (`Kura.Offline.apply_changes/2`), skips whatever no longer makes sense, and returns a fresh snapshot. The offline screens probe `/offline/state` every 5 s; once the server answers they send the queue and return to the real app. The normal app also sends a leftover queue when it opens or the browser comes back online. A 401 keeps the queue and asks for a sign-in.
- **CSRF.** The JSON endpoints use the session cookie (SameSite=Lax) and `POST /offline/sync` additionally requires the custom header `x-kura-offline: 1`, which cross-site pages cannot send.
- **Privacy.** Signing out clears the saved copy and the queue from the phone.
- **Install.** Web app manifest, icons (192, 512, Apple touch icon) and the usual meta tags; `viewport-fit=cover` with safe-area padding for iPhones.
- The offline screens' markup lives in JavaScript (`view.js`) and mirrors the LiveView markup. Changing the look of a screen means changing both.
- The pure parts of the client (`state.js`) are tested in Chrome (`test/js/offline_state_test.html`); there is no Node in this project.

## Consequences
- Offline writes are limited to check-off and un-check, as in the MVP. Anything else needs a connection.
- Stale data: offline screens show the copy from the last time the app was open online. Two people changing things offline overwrite each other per entry (last sync wins).
- The service worker must be reachable at `/sw.js` through the reverse proxy and must not be cached by it.
- Service workers need HTTPS; the production setup (Traefik) provides it, and in development `tailscale serve` does.
- The JavaScript is not covered by `mix test`.
